# Store Stock Management Project Bible

Stable description of the system. Details live in the referenced documents; nothing here is copied from them.

## Purpose

A web app that tells each store how much stock to order or make, and on which day, so that every item is used inside its usable days. Spoilage, waste and early use of immature stock go down. The calculation is automatic and the store can adjust it.

Success means: fewer expired and damaged items, no dough used before its first usable day because of a shortage, a short list each day that tells the store what to order or make, and an audit trail of what was counted and changed.

## Business problem

The stores keep a daily inventory sheet in Excel. It records beginning stock, received, wastage and ending count, but it has no production date (PD), no forecast and no link to shelf life. Stores decide quantities by experience.

What Leo described:

1. Dough is often used on day 1 or day 2 because the stock ran out or the forecast was wrong. The rule says dough is usable only from day 3. This is not visible today because the sheet has no PD.
2. Items with a short shelf life expire: carbo is 4 days from PD (from the commissary) and palabok is 5 days.
3. Delivery schedules differ by store (1 to 3 deliveries a week, different order and receive days) and some stores make their own dough.

Baseline from one store and one week (AP Malate, P12W2, read from the workbook): spoilage PHP 3,568 on net sales of about PHP 1.38 million (about 0.26%). Dough waste was 19 pieces (PHP 448): 3 expired and 16 damaged. The largest expired item was palabok sauce. One store and one week is not a trend; it shows where to look.

## Value

This is an internal tool. It has no revenue. Its value is measured by:

| Measure | Source |
| --- | --- |
| Expired and damaged pieces and cost, by item, store and period | waste_events |
| Dough used before its first usable day (when PD is recorded) | batches and daily_counts |
| Days with a shortage in the 7-day plan | forecast |
| Spoilage as a percent of net sales (target not set, gate G-09) | store sheet, outside this system |

## Architecture principles

1. Four layers: screens, API client, services, repository. A layer calls only the layers below it. Only the repository touches the database.
2. Role checks happen on the server for every call. Hiding a button is not security.
3. IDs are generated by the server, carry a prefix, and are never typed.
4. Every table has audit columns; every change is written to `audit_log`; records are deactivated, not deleted.
5. The forecast is computed when read and is not stored. Only the quantity the store approves is stored.
6. Rules are data (item rules, supply slots, settings), not code, so changing a schedule needs no release.
7. Free tier first (ADR-0001). If the app outgrows it, only the repository and the transport change.

## Constraints

Free-tier limits of Cloudflare (see [ARCHITECTURE](ARCHITECTURE.md) section 7). Leo manages the work from an Android tablet with limited token budget, so documents stay short and the repository holds the approved plan.
